
# Лабораторная работа: Настройка и тестирование отказоустойчивого набора реплик MongoDB

## 1. Цель работы

Получить практические навыки проектирования, развертывания, настройки и эксплуатации набора реплик (Replica Set) MongoDB в среде, приближенной к production. В ходе работы вы:

- Развернете набор реплик из трех узлов с внутренней аутентификацией.
- Настроите приоритеты узлов и параметры согласованности чтения/записи.
- Проверите репликацию данных и устойчивость к отказу.
- Освоите методы мониторинга состояния репликации и настройки журнала операций (oplog).


## 2. Теоретическая справка

**Набор реплик** — это группа экземпляров `mongod`, поддерживающих один и тот же набор данных. Один узел является **первичным (Primary)** и принимает все операции записи, остальные — **вторичные (Secondary)** , которые реплицируют данные с первичного через журнал операций (oplog).

Минимальная рекомендуемая конфигурация для production — **три узла с данными** (без арбитра). Это обеспечивает автоматическое переключение при отказе (кворум 2 из 3) и возможность распределения чтения. Использование арбитра не рекомендуется, так как он не хранит данные и не может стать первичным.

Все узлы должны использовать **одинаковую мажорную версию MongoDB** и разрешать друг друга по **DNS-именам**, а не по IP-адресам.


## 3. Окружение лабораторной работы

Для выполнения работы потребуется три сервера (контейнеры) с следующей конфигурацией:

| Роль | Hostname | IP-адрес (пример) | Приоритет |
|------|----------|-------------------|-----------|
| Узел 1 (Primary)   | `mongo1` | `172.16.0.101` | 2 |
| Узел 2 (Secondary) | `mongo2` | `172.16.0.102` | 1 |
| Узел 3 (Secondary) | `mongo3` | `172.16.0.103` | 1 |

IP-адрес присваевается автоматически при установке через Docker

**Требования к серверам:** ОС Ubuntu 22.04 LTS (или аналог), не менее 4 ГБ ОЗУ (рекомендуется 8 ГБ), SSD-накопитель, синхронизация времени через NTP, сетевой доступ между всеми узлами.

**Необходимое ПО:** MongoDB 8.0 (одинаковой версии на всех узлах), `mongosh`.



## 4. Пошаговый ход выполнения

### Шаг 1. Подготовка серверов

На **каждом** из трех серверов выполните обновление системы и утилит.

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y gnupg curl wget net-tools
```

---

### Шаг 2. Создание файла ключей для внутренней аутентификации


Сгенерируйте keyfile **на хост-машине**, а не внутри контейнера, чтобы обеспечить одинаковый файл для всех узлов и избежать проблем с правами доступа.

```bash
mkdir -p ./mongo-docker
openssl rand -base64 756 > ./mongo-docker/mongo-keyfile
chmod 400 ./mongo-docker/mongo-keyfile
sudo chown 999:999 ./mongo-docker/mongo-keyfile
```

**Критически важный момент:** MongoDB внутри официального Docker-образа работает под пользователем с **UID 999**. Если владелец keyfile на хосте имеет другой UID, `mongod` внутри контейнера не сможет прочитать файл, даже если на хосте выставлены права `400`. Поэтому необходимо выполнить `chown 999:999` (или использовать `--user 999:999` при запуске контейнера, но проще исправить владельца файла).

> **Профессиональный совет:** В production не храните keyfile в открытом виде на хосте. Используйте Docker secrets или, как минимум, bind mount с ограниченными правами. Официальное руководство MongoDB также подчеркивает необходимость контроля доступа к keyfile.

### Шаг 3. Создание `docker-compose.yml`

Создайте файл `docker-compose.yml` в директории `./mongo-docker`:
```yaml
networks:
  mongo_net:
    driver: bridge

volumes:
  mongo1_data:
  mongo2_data:
  mongo3_data:

services:
  mongo1:
    image: mongo:8.0
    container_name: mongo1
    hostname: mongo1
    restart: unless-stopped
    networks:
      - mongo_net
    ports:
      - "27017:27017"
    environment:
      MONGO_INITDB_ROOT_USERNAME: admin
      MONGO_INITDB_ROOT_PASSWORD: "${MONGO_ROOT_PASSWORD}"
    volumes:
      - mongo1_data:/data/db
      - ./mongo-keyfile:/etc/mongo/keyfile:ro
    command: >
      mongod --replSet rs0
      --keyFile /etc/mongo/keyfile
      --bind_ip_all
      --auth

  mongo2:
    image: mongo:8.0
    container_name: mongo2
    hostname: mongo2
    restart: unless-stopped
    networks:
      - mongo_net
    ports:
      - "27018:27017"
    environment:
      MONGO_INITDB_ROOT_USERNAME: admin
      MONGO_INITDB_ROOT_PASSWORD: "${MONGO_ROOT_PASSWORD}"
    volumes:
      - mongo2_data:/data/db
      - ./mongo-keyfile:/etc/mongo/keyfile:ro
    command: >
      mongod --replSet rs0
      --keyFile /etc/mongo/keyfile
      --bind_ip_all
      --auth

  mongo3:
    image: mongo:8.0
    container_name: mongo3
    hostname: mongo3
    restart: unless-stopped
    networks:
      - mongo_net
    ports:
      - "27019:27017"
    environment:
      MONGO_INITDB_ROOT_USERNAME: admin
      MONGO_INITDB_ROOT_PASSWORD: "${MONGO_ROOT_PASSWORD}"
    volumes:
      - mongo3_data:/data/db
      - ./mongo-keyfile:/etc/mongo/keyfile:ro
    command: >
      mongod --replSet rs0
      --keyFile /etc/mongo/keyfile
      --bind_ip_all
      --auth

```
**Пояснения к конфигурации:**

- Переменная `MONGO_ROOT_PASSWORD` должна быть задана в `.env`-файле или передана через окружение; не храните пароль в открытом виде в compose-файле.
- **`--keyFile` и `--auth`**: включают внутреннюю аутентификацию между узлами и авторизацию клиентов.
- **`--bind_ip_all`**: внутри изолированной Docker-сети это безопасно и необходимо для доступности узлов друг для друга.
- **Named volumes** (`mongo1_data` и т.д.): обеспечивают сохранность данных при перезапуске контейнеров. Без volumes данные будут утеряны при удалении контейнера.
- **`restart: unless-stopped`**: контейнеры будут автоматически перезапускаться после сбоя или перезагрузки хоста.

### Шаг5. Инициализация набора реплик

Подключитесь к **узлу 1** (`mongo1`) через `mongosh` и выполните инициализацию. Используйте **DNS-имена**, а не IP-адреса, и задайте более высокий приоритет для узла 1, чтобы он стал первичным после инициализации:

```javascript
docker exec -it mongo1 mongosh -u admin -p 'StrongP@ssw0rd!' --authenticationDatabase admin 

rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "mongo1:27017", priority: 2 },
    { _id: 1, host: "mongo2:27017", priority: 1 },
    { _id: 2, host: "mongo3:27017", priority: 1 }
  ]
})
```

Ожидаемый ответ: `{ ok: 1 }`.

### Шаг6. Проверка состояния набора реплик:**

```bash
docker exec -it mongo1 mongosh -u admin -p 'StrongP@ssw0rd!' --authenticationDatabase admin 
```

Выполните на первичном узле:

```javascript
rs.status()
```

Убедитесь, что вывод содержит одного члена в состоянии `PRIMARY` и двух в состоянии `SECONDARY`. Также проверьте карту ролей:

```javascript
db.hello()
```

Поле `isWritablePrimary: true` подтверждает, что узел является первичным.


### Шаг 7. Тестирование репликации данных

Подключитесь к первичному узлу **с аутентификацией** и создайте тестовые данные:


```javascript
use labdb
db.test.insertOne({ message: "Replication test", ts: new Date() })
```

Подключитесь к **вторичному** узлу (`mongo2` или `mongo3`) и разрешите чтение со вторичного:

```javascript
mongosh --host mongo2 --port 27017 -u admin -p 'StrongP@ssw0rd!' --authenticationDatabase admin
db.getMongo().setReadPref('secondary')  // Разрешает чтение с этого secondary
use labdb
db.test.find()
```

Документ должен присутствовать на вторичном узле. Это подтверждает работающую репликацию.

### Шаг 8. Настройка согласованности чтения и записи (тюнинг)

По умолчанию MongoDB использует `writeConcern: { w: 1 }` (подтверждение только от первичного) и `readPreference: "primary"`. Для production-сценариев, где важна устойчивость к отказу, рекомендуется повышать уровень согласованности.

**Настройка `writeConcern` на уровне коллекции:**

```javascript
use labdb
db.test.insertOne(
  { message: "Durable write", ts: new Date() },
  { writeConcern: { w: "majority", wtimeout: 5000 } }
)
```

`w: "majority"` гарантирует, что запись подтверждена большинством голосующих узлов (2 из 3) и переживет отказ одного узла.

**Настройка `readPreference` на уровне клиента** (пример для строки подключения):

```text
mongodb://admin:...@mongo1:27017,mongo2:27017,mongo3:27017/admin?replicaSet=rs0&readPreference=secondaryPreferred
```

`secondaryPreferred` предпочитает чтение со вторичных узлов, что снижает нагрузку на первичный, но допускает чтение устаревших данных (eventual consistency).

**Комбинированный подход:** Для критичных операций используйте `readConcern: "majority"` в сочетании с `writeConcern: "majority"`. Это гарантирует, что чтение увидит только те данные, которые были подтверждены большинством и не будут откатаны.

### Шаг 9. Проверка failover в Docker-среде

Остановите контейнер с первичным узлом:

```bash
docker stop mongo1
```

Проверьте состояние на любом из оставшихся узлов:

```bash
docker exec -it mongo2 mongosh -u admin -p 'StrongP@ssw0rd!' --authenticationDatabase admin --eval "rs.status()"
```

Один из оставшихся контейнеров должен перейти в состояние `PRIMARY`. Затем запустите `mongo1` снова:

```bash
docker start mongo1
```

После восстановления он автоматически синхронизируется и станет `SECONDARY` (или инициирует выборы, если его приоритет выше, что нормально).
